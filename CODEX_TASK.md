# CODEX TASK — BAD READING CLUB MVP

Ты senior full-stack разработчик. Реализуй **работающий MVP** книжного клуба на основе требований и прикреплённых визуальных референсов. Не ограничивайся планом или демонстрационными экранами: создай проект, файлы, миграции, тесты/проверки и документацию.

## 1. Приоритеты

1. **Редактирование всего контента через собственную админку**: организатор не программист и не должен заходить в GitHub, писать JSON, SQL или запускать деплой.
2. **Бесплатный стек**: GitHub Pages + Supabase Free, без платных обязательных сервисов.
3. **Доступ из РФ без VPN**: сайт должен работать без обязательных сторонних CDN на клиенте; доступность API Supabase зависит от сети и проверяется отдельно. Предусмотри понятные сообщения при сетевых ошибках.
4. **Сдержанный дизайн**, точно опирающийся на `design/reference-main.png`.
5. Простота архитектуры и сопровождения.

## 2. Стек

- React + Vite + TypeScript
- Tailwind CSS
- React Router (для GitHub Pages используй HashRouter либо проверенный 404 fallback)
- Supabase JS SDK: PostgreSQL, Auth, Storage
- GitHub Actions + GitHub Pages для статического фронтенда
- Без Next.js, собственного Node.js API, платных сервисов и сторонней CMS.

## 3. Дизайн

**Обязательно открой и изучи изображения:**
- `design/reference-main.png` — основной, минималистичный концепт.
- `design/reference-secondary.png` — дополнительный концепт.
- `design/original-brand-reference.jpg` — исходный фирменный референс.

Молочный фон, тёмно-зелёные акценты, элегантная serif-типографика заголовков, аккуратный sans-serif для интерфейса, тонкие разделители, просторная композиция, книжные обложки как главные визуальные элементы. Никаких ярких градиентов или перегруженных декоративных элементов. Адаптивность от мобильного экрана до десктопа. Создай переиспользуемые компоненты и общую дизайн-систему. Референсы — ориентир, не вставляй изображения целиком в качестве UI. Макетные даты, оценки, фотографии и отзывы не считать реальными данными.

## 4. Публичные страницы (без логина)

### Главная `/`
- Логотип/название BAD READING CLUB.
- Ближайшая встреча (дата, время, место, книга) из базы по ближайшей будущей дате.
- Текущая/следующая книга с обложкой и переходом на её страницу.
- Краткая информация о клубе.
- Следующая книга: **«К востоку от Эдема», Джон Стейнбек**. Не придумывай реальную дату и место встречи: показывай «Уточняется», пока админ их не заполнил.

### Планы `/plans`
- Прошедшие и будущие книги/встречи в хронологическом порядке.
- Название, автор, дата, статус (в планах / читаем / прочитано).
- Ссылки на страницы книг.

### Рейтинг `/ratings`
- Список книг с итоговыми оценками, сортировка по убыванию.
- Итоговые оценки **вносит администратор после голосования в Telegram**, пользователи на сайте не голосуют.
- Не показывать вымышленные оценки. Отсутствие оценки отображать корректно.

### Книга `/books/:slug`
- Обложка, автор, название, описание, статус, итоговая оценка, связанная встреча.
- Отзывы с именем автора/псевдонимом, текстом; отзывы вводит администратор.
- Фотогалерея со встречи, если фото есть.
- Пустые состояния, если отзывов, фотографий или оценки пока нет.

### Информация о встрече
- Ближайшая встреча показывается на главной; можно реализовать отдельную страницу `/meeting` для подробностей.
- Никаких отметок посещаемости и кнопки «Я иду».

## 5. Админка `/admin`

**Только один или несколько явно назначенных администраторов.** У обычных посетителей нет регистрации, аккаунтов, личных оценок и доступа к админке.

Сделай дружелюбную веб-админку:
- Вход/выход через Supabase Auth (email + пароль).
- Список, создание, редактирование и удаление книг; обложка, описание, статус, итоговая оценка.
- Управление встречами: книга, дата/время, место, примечания, фото.
- Управление отзывами: книга, имя автора/псевдоним, текст, при необходимости оценка отзыва как отдельное необязательное поле (не путать с итоговой оценкой книги).
- Настройки клуба: название, описание, публичные ссылки.
- Подтверждения удаления, валидация, состояния загрузки, ошибки и успешное сохранение.
- Изменения сохраняются в Supabase и появляются на публичном сайте без коммита/деплоя.
- Администратору не требуется GitHub.

## 6. Supabase и безопасность

Спроектируй SQL-миграции с таблицами, например:
- `books`: id UUID, slug unique, title, author, description, cover_path, status, final_rating nullable, timestamps, published flag.
- `meetings`: id UUID, book_id FK, starts_at nullable, place nullable, notes, timestamps, published flag.
- `reviews`: id UUID, book_id FK, author_name, body, optional rating, timestamps, published flag.
- `meeting_photos`: id UUID, meeting_id FK, storage_path, caption, sort_order.
- `club_settings`: singleton configuration.
- `admin_users`: user_id UUID references auth.users(id).

Допускается корректировать схему ради чистой модели. Используй ограничения, индексы, внешние ключи, каскадные правила там, где они осмысленны.

**Обязательно включи RLS для всех таблиц**. Публичный `SELECT` только для опубликованных данных. Запись/изменение/удаление только если `auth.uid()` входит в `admin_users`. Запрети публичное изменение `admin_users`, чтобы никто не мог самостоятельно назначить себе роль администратора. Первого администратора добавляют вручную через защищённый SQL Editor после создания Auth-пользователя; задокументируй процедуру. Проверка доступа должна работать на уровне БД и Storage, не только в React.

Storage: публичное чтение опубликованных обложек/фото, загрузка и удаление только администратором; валидация MIME/размера, клиентское уменьшение фото, безопасные пути, очистка файлов при удалении сущностей. Не помещай `service_role`/secret keys в браузер. Используй только publishable key в `VITE_` переменных. Отключи публичную регистрацию в Supabase и опиши настройку.

## 8. Структура и качество

- Компоненты, страницы, features, hooks, lib, types.
- Типизированный слой работы с Supabase; по возможности сгенерированные типы БД либо вручную описанные контракты.
- Понятные empty/loading/error states, доступность, клавиатурная навигация, семантическая разметка.
- Базовая SEO-разметка (в пределах возможностей SPA), корректные title/description.
- Нет зависимости от Google Fonts CDN или иных внешних ресурсов, которые могут блокироваться в РФ; используй системные шрифты или локально размещённые разрешённые шрифты.
- Не включай в репозиторий реальные секреты, пароли, токены.

## 9. Развёртывание

- `.env.example` с `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`.

- GitHub Actions workflow для сборки и публикации на GitHub Pages.
- README: локальный запуск, создание Supabase, применение миграций, создание администратора, Storage, переменные окружения, GitHub Pages, проверка из РФ.

## 11. Порядок реализации и критерии готовности

1. Изучи референсы и существующие файлы, сформируй короткий план.
2. Создай приложение, дизайн-систему и публичные страницы.
3. Создай миграции Supabase с RLS и Storage-политиками.
4. Реализуй вход админа и полный CRUD через интерфейс.
5. Подключи реальное чтение/запись Supabase, не оставляй моки в финальной реализации.
6. Настрой GitHub Pages CI/CD и документацию.
7. Запусти `npm install`, проверку типов, lint (если настроен), `npm run build`, исправь ошибки.
8. Проверь сценарии: анонимный просмотр, запрет анонимной записи, админское создание книги, изменение рейтинга, публикация встречи, загрузка фото, удаление.
9. В конце перечисли сделанное, результаты проверок и необходимые ручные действия. Не заявляй, что интеграционные тесты с реальным Supabase прошли, если ключи/проект не были предоставлены.

## 12. Важная граница

В рамках текущего MVP GitHub используется только для исходников и публикации фронтенда. Организатор клуба не взаимодействует с GitHub. Сохранение контента всегда идёт в Supabase через админку.
